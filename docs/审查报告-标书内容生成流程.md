# 标书内容生成流程审查报告与优化方案

审查日期：2026-08-06
审查范围：`OutlineDetailView.vue` 及关联组件、后端 `outline` / `common` / `task_queue` 应用、部署层超时配置。

---

## 一、问题 1：内容生成按钮流程审查

整体防重复点击、失败复位、错误提示大体健全，但有 2 个实质功能错误。

### 1.1【中】单章"开始生成"传了空的 analysis_result，后端自动分析分支永不触发

- 位置：`frontend/src/views/outline/OutlineDetailView.vue:1271-1283`
- 现象：前端把初始值 `{keywords:[], knowledge_types:[], requirement_types:[], background:'', suggested_prompt:''}` 原样传给后端。该 dict 在 Python 侧为真值，导致后端 `views.py:1213-1218`"未传分析结果则自动分析"的分支永远不会触发——用户不点"AI生成"直接点"开始生成"时，用全空分析结果生成正文，质量受损且无任何提示。

### 1.2【中】AI 分析/单章生成接口沿用 axios 默认 30s 超时

- 位置：`frontend/src/api/http.ts:28`（timeout: 30000）、`frontend/src/api/outline.ts:316-318`
- `analyzeSection` 是同步 LLM 调用（`views.py:1087-1092`），LLM 超过 30s 前端即报"分析失败"，但后端仍在执行。对比 `reviewOutline` 已专门覆盖为 180s（`outline.ts:242-246`），说明项目已知此风险但只改了一处。

### 1.3【低】生成矩阵按钮无 loading、可连点

- 位置：`OutlineDetailView.vue:1040-1063`。后端幂等（已有进行中任务返回 existing，`views.py:358-387`），后果轻微，但建议加 loading。

其余按钮（批量生成、生成 Word、下载、全局事实提取等）均有 loading 防重复 + finally 复位 + 错误提示，无问题。

## 二、问题 2：任务完成后进度条显示不正确

### 2.1【高】矩阵进度对话框完成态枚举与后端不匹配（核心 bug）

后端矩阵任务终态是 **`completed`**（`backend/apps/outline/constants.py:224`，SSE 也在 `completed` 时发 done，`views_sse.py:141-148`），但 `frontend/src/components/outline/MatrixProgressDialog.vue` 全部按 **`success`** 判断：

| 位置 | 影响 |
|---|---|
| `:65` 完成 Alert `status === 'success'` | 永不显示"已完成"提示 |
| `:179` 进度条状态只认 `success` | 完成后仍是蓝色进行中样式 |
| `:100` footer 关闭按钮不含 `completed` | 任务完成后底部一个按钮都没有，只能点右上角 X |
| `:250` 轮询终止条件不含 `completed` | SSE 断开降级轮询后，任务已完成也会每 3 秒**永远轮询**，直到手动关对话框 |
| `:279-288` 完成消息无 `completed` 分支 | 完成时静默，无任何提示 |

综合效果：矩阵生成完成后，对话框停在 100% 蓝条、无"完成"字样、无按钮、无提示——**看起来就是"还在进行中/卡住了"，这正是用户反馈的根因**。

对比：`BatchProgressDialog.vue` 全程正确使用 `completed`，批量进度对话框无此问题。

### 2.2【高】后端存在多条"状态永不回写终态"路径

- **B1（中）**：`batch_section_generation_task` 外层 try 只有 finally 没有 except（`backend/apps/outline/tasks.py:515-571`）。chord 派发之外的异常（取任务、`refresh_from_db`、查子项时的数据库错误）直接抛给 Celery，GenerationTask 永远停在 RUNNING。
- **B2（高）**：兜底回收不覆盖批量任务。`reconcile_stale_async_tasks`（`backend/apps/common/tasks.py:13`）只回收 RUNNING 的 AsyncTask、PromptRun、GENERATING 的 Outline、**矩阵类** GenerationTask（`_reclaim_stale_matrix_tasks` `:137-175`）。`section_batch_generation` 类型卡 RUNNING/PENDING 时没有任何自动回收，且 `create_batch_task` 把 RUNNING/PENDING 视为占用（`batch_generation_service.py:276-288`）——**该大纲从此无法再发起批量生成**，目前只能靠队列管理页手动"强制结束"。
- **B3（高）**：Celery 投递失败被静默吞掉。`enqueue_after_commit._enqueue` 捕获所有异常只记日志（`backend/apps/common/tasks_utils.py:48-57`），任务保持 PENDING，而 reconcile 只回收 RUNNING。受害者：
  - 全局事实提取：`get_active_extract_task` 把 PENDING 算活跃（`global_fact_service.py:41`），前端轮询永远看到"进行中"，且幂等逻辑使重新点击返回同一个死任务，永远无法恢复；
  - 矩阵生成 `matrix_service.py:173-176`、批量生成 `batch_generation_service.py:352`、目录完善 `views.py:789-797` 同构。
- **B4（低）**：全局事实工作流 try 之前有三处裸查询（`global_fact_workflow.py:47-49`），大纲被删等边缘场景会使任务停 PENDING。

### 2.3【低-中】进度对话框其他问题

- `MatrixProgressDialog.vue:226` SSE 更新把 `updated_at` 硬编码为 `''`，`isStuck` 恒为 false，"强制重置"按钮在 SSE 模式下永不出现。
- 父组件批量 SSE `onError`（`OutlineDetailView.vue:990-994`）只停 SSE 不清 `batchProgress`，迷你进度条永远停在转圈状态。
- 任务完成后无法再次查看历史进度：矩阵对话框仅在 `is_generating` 时自动打开（`:1020-1032`）；批量完成后 `batchProgress` 置 null（`:972`）。再点"生成矩阵"会直接发起新任务而非查看上次结果。
- SSE 60 秒空闲超时与长 LLM 调用冲突（`views_sse.py:84,151-153`）：单章 LLM 最长 900s，期间计数不变 → SSE 必然中途断开，前端只提示"任务仍在后台运行"，之后进度不再更新（`OutlineDetailView.vue:995-998`）。
- 单章生成轮询的 catch 分支静默清定时器（`OutlineDetailView.vue:1330-1333`），接口报错时用户无提示。
- `checkActiveBatchTask` 活跃态列表不含 `cancel_requested`（`:891`），取消中的窗口期进度条直接消失。

轮询/SSE 清理本身无泄漏：各对话框关闭/卸载均正确停止定时器，单章轮询有 120 次上限。

## 三、问题 3："目录校验"一直转圈、不知是否成功

### 3.1【高】根因一：同步接口与各层超时不匹配，慢调用必失败

- 路径：`POST /api/outlines/{id}/review/` → `views.py:738-751` 在请求内**同步**执行 `OutlineReviewService.review_outline()`（`outline_review_service.py:41-52`），串行 1~2 次 LLM 调用，无任务机制、无进度回写。
- 超时不匹配：LLM 单次调用超时下限写死 **900s**（`deepseek_client.py:54-59`）且默认重试 2 次；而 gunicorn worker 超时 **120s**（`docker-compose.yml:50`）、nginx 300s、前端 axios 180s（`outline.ts:244`）。**任意一次 LLM 超过 120s，gunicorn 杀 worker，请求 502，`review_status` 永远不写回**。
- 另一个坑：`_review_outline` AI 调用失败时保守返回 `passed=False` 并把错误塞进 suggestions（`outline_review_service.py:300-302`），会把"AI 调用失败"伪装成"审核未通过"落库。

### 3.2【高】根因二：成功路径零反馈

- 指引面板按钮：`WorkflowGuidePanel.vue:52-54` → `OutlineDetailView.vue:104` `@review="handleReviewOutline(false)"`，显式传 `openDialog=false`。
- `handleReviewOutline` 成功分支没有 `ElMessage.success`（`:704-719`，对比失败分支有 error 提示）→ 转圈停止后不弹结果对话框、无任何消息，只有按钮颜色悄悄变化。用户完全无法感知"成功了"。
- 同一功能两个入口反馈不一致：顶部"更多操作→目录审核"走默认 `openDialog=true`（`:812`）会弹窗；指引面板"目录校验"不弹。
- 若超 180s，axios 超时进 catch，`e.response` 为 undefined，提示统一的"目录校验失败"——但后端可能已写入结果，提示有误导性。

## 四、优化方案（按优先级）

### P0：立即修复（低成本、直接解决用户三个问题）

1. **矩阵对话框枚举对齐**：`MatrixProgressDialog.vue` 把 `success` 判断全部改为 `completed`（第 65、100、179、250、279 行共 5 处），或定义 `TERMINAL_STATUSES = ['completed','failed','partial_success','cancelled']` 常量统一判断。
2. **目录校验成功反馈**：`handleReviewOutline` 成功分支加 `ElMessage.success(passed ? '目录校验通过' : '校验完成，存在 N 条修改建议')`；指引面板入口改为 `openDialog=true` 或至少在未通过时弹结果对话框。
3. **目录校验同步改异步**（彻底方案）：复用现有 AsyncTask 模式，把 `review_outline` 改为 Celery 任务 + 前端轮询进度；若短期不改架构，先把 gunicorn `--timeout` 提升到 ≥300 并把前端超时对齐，同时在请求期间给出"预计需要 1-2 分钟"的提示。
4. **修复"AI 失败伪装成审核未通过"**：`outline_review_service.py:300-302` AI 调用异常应向上抛出让接口返回 500，而不是落库 `review_status='failed'`。

### P1：状态可靠性（消除"永远进行中"）

5. `batch_section_generation_task` 外层补 `except Exception` 回写 FAILED（`tasks.py:515-571`）。
6. `reconcile_stale_async_tasks` 覆盖 `section_batch_generation` 类型 GenerationTask，并回收超时 PENDING 任务（`common/tasks.py`）。
7. Celery 投递失败时把任务标记为 FAILED 而非静默吞掉（`tasks_utils.py:48-57` 记日志的同时回写状态）。
8. 全局事实工作流的三处裸查询移入 try（`global_fact_workflow.py:47-49`）。

### P2：体验与一致性

9. `analyzeSection` 等同步 LLM 接口超时统一提升到 180s（对齐 reviewOutline 的做法）。
10. 前端修复：批量 SSE `onError` 清空 `batchProgress`；SSE `updated_at` 不再硬编码空串；`checkActiveBatchTask` 活跃态补 `cancel_requested`；单章轮询 catch 加错误提示。
11. 任务完成后支持"查看上次进度"：矩阵/批量完成后保留入口（如状态徽标可点击重开对话框，拉取最新状态展示终态）。
12. SSE 空闲超时与 LLM 长调用适配：后端 SSE 在无数据变化时发送心跳注释而非断开，或把空闲阈值提高到 ≥180s；前端收到 timeout 后自动重连而不是停止监听。
13. 生成矩阵按钮加 loading 防连点。
14. 修复"空 analysis_result 绕过自动分析"：前端未分析时不传该字段（或传 null），由后端触发自动分析。
15. 清理死代码 `MatrixStatusBadge.vue`（全项目无引用）。

### 建议实施顺序

P0 的 1、2、4 为纯前端/小改动，一个迭代即可上线，直接消除"进度条不正确"和"校验不知道是否成功"两个用户感知最强的问题；P0-3 的异步化与 P1 的状态回收作为第二个迭代。

## 附：其他发现

- `GlobalFactTaskStatus`（`constants.py:257-276`）疑似废弃：实际使用的是 AsyncTask 的 pending/running/retrying/success/failed，两套枚举并存易误导后续开发。
- `resume_task` 中 `BatchGenerationTaskItem.objects.filter(status='pending').update(status='pending')` 为无效语句（`batch_generation_service.py:406-409`），worker 崩溃后卡 running 的子项永远不会被恢复处理。
- `generate_section_task` 异常处理器内部裸查（`tasks.py:477,483`），记录恰被删除时异常处理器自身抛错。
